# Configuration

Every value below is read from the environment at startup. The defaults suit a developer's machine; a
deployment supplies its own.

| Variable                              | What it sets                                                                                                                                                              | Default                                      | Required                 | Secret |
|---------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------|--------------------------|--------|
| `DB_JDBC_URL`                         | the database the service reads and writes                                                                                                                                   | `jdbc:postgresql://localhost:5432/ledger-db` | yes                      | no     |
| `DB_USER`                             | the database account. It needs the `REPLICATION` attribute for the replication slot, which a managed database does not grant by default                                      | `ledger-user`                                | yes                      | no     |
| `DB_PASSWORD`                         | the password for that account                                                                                                                                               | *(a local placeholder)*                      | yes                      | yes    |
| `TELEGRAM_BOT_TOKEN`                  | which bot the service collects messages for and acts as. It sits in every Bot API request URL, so it reaches wherever those reach                                            | *(none)*                                     | when polling is on       | yes    |
| `TELEGRAM_POLLING_ENABLED`            | whether the service collects Telegram messages at all. On with no bot token stops startup; off boots without one                                                             | `true`                                       | no                       | no     |
| `TELEGRAM_API_URL`                    | where Telegram's Bot API is reached. A deployment leaves it alone ([ADR 0001](adr/0001-telegram-updates-arrive-by-long-polling.md))                                          | Telegram's own address                       | no                       | no     |
| `TELEGRAM_LOGIN_MAX_AGE`              | how old a Telegram sign-in may be and still be accepted, which bounds how long a captured payload stays replayable                                                           | `1d`                                         | no                       | no     |
| `AI_CONNECTOR_GRPC_TARGET`            | where the AI Connector's gRPC server is reached. How a target pointing nowhere shows: [AI Connector Service](contracts/out/ai-connector.md)                                  | `static://localhost:1001`                    | no                       | no     |
| `MCP_ENABLED`                         | whether the MCP server endpoint is served at all. Off leaves the service running with that endpoint gone, the session API untouched                                          | `true`                                       | no                       | no     |
| `TOKEN_SIGNING_KEYSTORE`              | where the keystore signing every token the service issues is read from. The default is committed to this repository, its password with it. It is read once at startup, and one that cannot be opened stops it | the committed development keystore | yes         | no     |
| `TOKEN_SIGNING_KEYSTORE_PASSWORD`     | the password for that keystore                                                                                                                                              | *(a local placeholder)*                      | yes                      | yes    |
| `TOKEN_SIGNING_KEY_ALIAS`             | which key pair in the keystore signs and verifies those tokens. No key under the alias stops startup                                                                         | `mcp-signing`                                | with a supplied keystore | no     |
| `MCP_JWT_TTL`                         | how long a minted MCP token is valid, and the longest lifetime an arriving one may claim; more is refused ([the ledger's tools](contracts/in/mcp.md))                        | `2m`                                         | no                       | no     |
| `SESSION_JWT_TTL`                     | the same, for a browser session token ([the session API](contracts/in/web-session-api.md))                                                                                   | `7d`                                         | no                       | no     |
| `WEB_SESSION_COOKIE_NAME`             | which cookie carries the browser session                                                                                                                                    | `fb_session`                                 | no                       | no     |
| `WEB_SESSION_COOKIE_SECURE`           | whether that cookie is sent over HTTPS only. A browser discards a secure cookie sent over plain HTTP                                                                         | `false`                                      | wherever HTTPS is served | no     |
| `WEB_SESSION_COOKIE_SAME_SITE`        | how that cookie behaves on a cross-site request. `Lax` suffices on one origin ([ADR 0014](../../docs/adr/0014-the-web-app-and-the-ledger-are-served-from-one-origin.md))     | `Lax`                                        | no                       | no     |
| `REPORT_CLEARING_POOL_CORE_SIZE`      | the clearing pool's core thread count. The pool runs the one piece of work this service does off the request thread ([Clear the emptied reports](usecases/clear-emptied-reports.md)) | `1`                                  | no                       | no     |
| `REPORT_CLEARING_POOL_MAX_SIZE`       | the clearing pool's maximum thread count                                                                                                                                    | `2`                                          | no                       | no     |
| `REPORT_CLEARING_POOL_QUEUE_CAPACITY` | how many clearing tasks wait; the rest are dropped, never run on the request thread. Raise it where a deployment serves more than one person's chats                         | `100`                                        | no                       | no     |
| `CDC_ENABLED`                         | whether the change-capture engine runs at all. Off lets the service run against a Postgres below `wal_level=logical`, and leaves the replication slot in place, still retaining log | `true`                | no                       | no     |
| `REDIS_URL`                           | where Redis is reached                                                                                                                                                      | `redis://localhost:6379`                     | no                       | no     |
| `REDIS_COMMAND_TIMEOUT`               | how long a Redis command may take before it is treated as a failure                                                                                                         | `2s`                                         | no                       | no     |
| `CDC_SLOT_NAME`                       | the replication slot the engine holds                                                                                                                                       | `finance_ledger_cdc`                         | no                       | no     |
| `CDC_STREAM_KEY`                      | the stream every change is written to                                                                                                                                       | `ledger.cdc`                                 | no                       | no     |
| `CDC_STREAM_MAX_LENGTH`               | roughly how many entries the stream keeps                                                                                                                                   | `100000`                                     | no                       | no     |
| `CDC_SNAPSHOT_MODE`                   | whether rows already in a captured table are published when the engine first starts. The one captured table is the outbox, which is [empty at rest](contracts/out/change-capture.md), so nothing is ever snapshotted whatever this reads | `no_data`   | no                       | no     |
| `CDC_HEARTBEAT_INTERVAL`              | how often the slot is moved on with no captured change                                                                                                                      | `30s`                                        | no                       | no     |
| `CDC_SLOT_MONITOR_INTERVAL`           | how often the slot and the outbox are read for the meters                                                                                                                   | `30s`                                        | no                       | no     |
| `CDC_RECOVERY_SECRET`                 | the header value [the recovery operation](contracts/in/operations.md#rebuilding-the-slot) demands. Blank or unset stops startup, whether or not capture is on. It travels as a header only, and is never logged | *(none)*      | yes                      | yes    |
| `MANAGEMENT_PORT`                     | where health, metrics and the recovery operation are served                                                                                                                 | `1010`                                       | no                       | no     |

A secret belongs in the deployment's secret store, never in a committed file or a log line.

**One key pair signs both tokens the service issues.** Rotating it rotates both at once.

## What the database is given, not the service

`max_slot_wal_keep_size` bounds the log a replication slot may retain. The service reads the effect through
`ledger_cdc_slot_retained_bytes` and cannot set the bound itself; what happens past it is
[Change capture](contracts/out/change-capture.md).

[Compose](../../infrastructure/docker-compose.yaml) passes it as `postgres -c max_slot_wal_keep_size=1GB`.
**A value passed that way cannot be widened without restarting the container**: a command-line setting outranks
`ALTER SYSTEM` plus `pg_reload_conf()`. `wal_level` cannot be changed without a restart at all.
